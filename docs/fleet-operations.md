# Fleet, collection routes and pickup evidence

## Implemented browser workflow

1. **Admin → User Manager:** create active Driver logins. Driver and supervisor duties are currently combined; there is no separate Supervisor selection. Legacy Supervisor logins/data are preserved, but access requires a linked driver profile and is scoped to that driver's assignments. Saving a legacy supervisor work title normalises it to Driver. Customer names stay uppercase; driver identities come from their linked `drivers.user_id`, never fixed demo IDs.
2. **Manager → Driver Assignment → Driver Profiles:** register/edit driver profiles, base zone, phone and availability. The old permanent vehicle text field is no longer needed; legacy values remain in storage but are not the source of vehicle allocation.
3. **Manager → Zones & Routes:** create/edit zone boundaries and route paths using the existing native Google Maps controls. Codes and an existing route's zone remain immutable. Open Route Details, configure active GPS-located customers in that zone, and arrange stop order. Changes apply to future assignments only.
4. **Manager → Driver Assignment → Route Assignments & Vehicles:** register vehicles and availability (`available`, `maintenance`, `inactive`), optionally with expected L/100 km. Assign an active route to an available driver/vehicle and service date. The retained `supervisor_id` field automatically receives the driver's user ID on new assignments; old assignments are not rewritten. The UI also offers route-stop configuration. One open assignment reserves each driver and vehicle until finished/cancelled, including future assignments; this version is not a multi-shift scheduling calendar.
5. **Driver → Dashboard / Assigned Pickups / Route:** the signed-in driver sees their assignments, vehicle, last reported position and route map. Open an assignment, start the route (optional odometer), then deliberately start GPS capture. Confirm each visited stop explicitly, optionally with a photo; complaint-flagged visits require a photo.
6. **Driver → Monitoring / Pickup Oversight:** monitor only that driver's assignments, including for legacy Supervisor logins. Managers/admins can monitor all. Fleet overview markers and trip details show movement, last fix, route deviation, GPS distance, stops and evidence. Lists poll every 30 seconds and details every 15 seconds while visible; this is near-live polling, not push notification infrastructure. Legacy supervisor URLs remain available for existing links.
7. **Accountant → Fuel & Cheques:** select a vehicle and driver, enter fuel issue date, litres, GHS price per litre and cheque number; the total is calculated automatically. A route link is optional and must match that vehicle/driver. Use Fuel / Route Analysis to filter by date/vehicle/driver, compare issued fuel with route distance, inspect route details and export the actual summary as CSV. Corrections use reasoned reversals.

All section/form/detail navigation uses the shared inline navigation and loading buttons. Evidence previews are private media dialogs. Normal shared MUI tables are used, not DataGrid.

## Tracking rules and limitations

- Browser geolocation requires **HTTPS or localhost**, device GPS/location permissions and an explicit work-tracking confirmation. Merely loading a dashboard does not start GPS capture. No coordinates are invented when the device has not transmitted.
- Browser callbacks are sampled at most every 10 seconds. A user/run-scoped localStorage buffer retains up to 500 points and retries uploads in small batches while the active route page is open; it is not a service worker or guaranteed background queue. Stored points older than 24 hours are discarded on reload. Unmounting stops capture; in-flight uploads are idempotent and cannot overwrite a new page's buffer. Use one tracking browser/device per assignment.
- Leaving the detail page, hiding the tab, losing OS permission or screen-lock/battery optimisation can interrupt capture. Stop capture and upload the buffer before finishing. A manager closing a route remotely prevents subsequent GPS ingestion; outstanding buffered points then cannot be added to the closed route. Photo forms are not offline-synchronised.
- Reliable screen-locked/background tracking, device binding, managed tablets, native Android foreground services and vehicle tracker protocols remain separate implementation work. A driver's device location is assumed to accompany the assigned vehicle; it is not tamper-proof vehicle telemetry. Keep the local server reachable from devices, and host the backend securely before field deployment. A phone accessing an HTTP LAN IP will not meet browser GPS requirements.
- The server validates timestamps/coordinates/accuracy, assigned-driver access and started route state. Repeated request keys are idempotent; different coordinates under the same key conflict. Updates are bounded to 120 stored submissions/minute/run.
- Accuracy worse than 50 m, out-of-order points, points before route start and implausible jumps exceeding 130 km/h are excluded from metrics. Distance uses accepted chronological GPS segments, suppresses small accuracy-related jitter, and **does not bridge gaps over 2 minutes**. Gaps are counted, and the displayed trail is split at gaps. This filtered estimate can undercount driving; it is not certified mileage.
- Latest fixes older than two minutes show **stale / no GPS**, never live/on-route. Movement/speed is inferred from accepted segments; missing/stale/first-fix speed is unknown. Low speeds display stopped/slow.
- Route adherence is measured against the saved LineString using metre-based point-to-segment distance. A deviation beyond the configured 30–1000 m corridor plus GPS accuracy is flagged only after three consecutive accepted outside points. This is a visual warning; there are no automatic SMS/push penalties. Draw the actual collection streets; a coarse line or a straight line between endpoints cannot reliably represent road adherence.
- Route planning does **not** invoke paid Directions/Routes/road snapping/optimisation services. Native map credentials/services remain as previously configured. Road-navigation calculations, turn-by-turn navigation and automatically optimised ordering are unfinished.

## Visits, complaints and evidence

- Within 50 m, an accepted fix marks a pending customer stop **visited**. It never marks it collected. Driver confirmation requires a fresh fix (within two minutes, accuracy ≤50 m) within 150 m of the assigned stop, an outcome (`collected` or `not_collected`) and a note.
- **Manager → Complaints Overview** and **Support → Ticket Management** now use real stored collection complaints rather than mock tickets. Staff select the correct customer, record the complaint and resolve it deliberately. Drivers (including legacy Supervisor logins) can read complaint records relevant to their assigned stops, not all customers.
- Open complaints are red on route maps and carry text warnings. Normal pending stops are blue, visited/not-collected amber and collected green. Colour is accompanied by status/name text. Photo requirements are frozen when assigning a previously flagged customer, and also checked against complaints opened later. Resolving a complaint does not erase an assignment's frozen evidence requirement. Collecting a bin does not automatically resolve a complaint.
- Drivers can capture/select one JPG/PNG/WebP per confirmed stop. The client previews/compresses to JPEG (target 1 MB, 1800 px, no EXIF). The server validates signature/MIME and a 5 MB cap, stores a random private filename in `server/uploads/pickup-evidence`, and serves it only through assignment-authorised JWT endpoints with `private, no-store`/`nosniff` headers. No public images URL or raw file key is returned with stop lists.
- Metadata and confirmation commit transactionally. A failed transaction removes its new file; a crash between file write and commit can still leave an unreferenced file. Back up the private upload directory alongside the DB and reconcile orphan files before any cleanup. Confirmed evidence is not overwritten by a new confirmation request.
- Photos and GPS are supporting records, not conclusive proof of collection/fuel misuse. Bin QR/RFID scanning, trusted camera/device attestation and supervisor evidence acceptance/rejection remain future work.
- Customer-login linking is still unfinished. The Customer Complaints page no longer reports mock submission success or exposes a hardcoded customer's history; it explains that support must record the complaint for now. Other historical support dashboard/detail templates outside the connected complaint register may still contain mock data.

## Fuel and cheque safeguards

- Fuel register entries are distinct from customer subscription billing. No customer bill, payment, ledger entry or SMS is produced by a fuel issue or schema change.
- Only Accountant/Admin/Super Admin can issue/reverse fuel; Managers can read the fuel register/reports. Drivers (including legacy Supervisor logins) see their route-linked net litres, but not fuel-register amounts/entries. New entries require a cheque number protected against duplicates across the register, even after reversal; cheque clearance/bank integration is **not** implemented.
- Amounts use integer pesewas, litres use integer thousandths and unit prices use 10,000 units/GHS (four decimals). Client and server calculate `(litresMilli × priceUnits + 50000) / 100000` with integer half-up rounding; the server does not trust a submitted total. Request keys/fingerprints, vehicle/driver row locks and unique references prevent duplicate postings. Issues are immutable; a reversal records its opposite and reason, with one reversal per original. Original issue date/reference remain visible and cannot be reused as a supposedly new payment.
- Reports filter fuel by issue date and routes by service date, aggregating each independently by vehicle/driver so multiple vouchers never multiply distance. Unlinked fuel remains in period totals but is never silently allocated to a trip. Period ratios are comparisons, not measured consumption. Fuel and route dates can differ; tank stock and partial routes affect interpretation.
- Legacy entries retain their exact recorded amounts and derive vehicle/driver through their original route. Missing historical unit prices remain unknown; absent issue dates are explicitly labelled as recorded-date fallbacks. Reversals retain the original effective issue date and reference.
- Start/end odometers are optional and end cannot precede start. Comparison uses odometer distance when both are available; otherwise it uses filtered GPS distance. `issuedLitresPer100Km` means **issued**, not consumed. The vehicle's expected L/100 km is frozen on assignment; changing its later baseline does not rewrite an old comparison.
- Tank opening/closing levels, actual refill receipts, fuel-card imports, idling/load/traffic adjustments, cheque printing/clearance and formal accounting/payment integrations are not included. Do not interpret a high issue-to-distance ratio as proven misuse.

## Data, permissions and rollout

`server/migrations/fleetOperations.js` adds the private fleet tables, foreign keys, ordered route stops, immutable trip snapshots, location/evidence records, open-resource uniqueness and fuel register. `server/migrations/fuelRegister.js` adds nullable vehicle/driver/date/unit-price/name-snapshot fields, foreign keys and a lookup index, and makes the route link optional without rewriting old financial values. Both modules are shared by initial setup/tests and have been applied directly to the local database; repeat application was verified. Before/after snapshots confirmed existing fuel, route, bill, ledger and SMS rows were unchanged. No standalone `migrate_*.js` runner is left for the user. Existing IDs and legacy pickup/assignment records were preserved. No real vehicles, trips, complaints, fuel postings or messages were seeded.

The connected run model intentionally does not fabricate/import the old `pickup_requests`/`driver_assignments` demo workloads. Existing legacy records remain intact; review outstanding legacy jobs before moving a driver to the new route workflow. Customer stops, route name/geometry, vehicle fuel baseline and complaint evidence requirements are frozen per assignment. Trip state transitions reserve/release resources transactionally, and finishing with unserved stops needs explicit acknowledgement/reason; those stops remain unserved.

`/api/fleet` rechecks current active user/role from the database, not just a JWT role claim. Driver and legacy Supervisor roles can read/update only runs belonging to their linked driver profile, never other drivers' runs merely because of an old `supervisor_id`. Only managers/admins configure resources/assignments; only accountants/admins post fuel. Support has complaint operations, not route tracking. Legacy administrative resource-write routes now also require the appropriate managerial/admin JWT role. Full legacy-API security hardening remains separate work.

Fuel APIs: `GET /api/fleet/fuel/options`, `GET /api/fleet/fuel`, `GET /api/fleet/fuel/:id`, `POST /api/fleet/fuel` and `POST /api/fleet/fuel/:id/reverse`. Options include up to 500 recent non-cancelled routes, plus an explicitly requested older route for a direct link. The former route-first fuel posting endpoint rejects writes and directs callers to the register.

Tracking/complaint/photo data is sensitive. Inform staff of work-only tracking, restrict device/server/database access, secure transport/backups and agree retention before production. No automatic telemetry/evidence deletion job is enabled. Route history is capped to the latest 200 assignments per list, trails to the latest 2000 accepted points, complaint lists to 500 and selection options to 5000 customers; larger deployments need server-side search/pagination/history retrieval and retention sizing. A route stop list is capped at 1000 selections.

## Verification

The combined disposable-MySQL suite passed **78 tests**, including **25 fleet tests**: current-role/assignment authorisation, concurrent resource reservations, snapshots, idempotency, lifecycle/release, GPS distance/jumps/gaps/staleness/deviation, visits versus collection, complaint photo requirements, private valid/invalid uploads, standalone vouchers, exact price rounding, duplicate references/reversals, independent fuel/distance aggregation, optional route validation, legacy financial preservation, merged supervisor ownership, availability edits and odometer comparisons. Synthetic evidence files are stored only in a uniquely named test directory and removed afterward; no real customers, trips, fuel or SMS are touched.

Run `npm run test:fleet` for focused fleet tests or `npm run test:billing` for the combined suite inside `server/`. Both include quick syntax checks. Client checks include focused lint, `node scripts/check-fleet-ui.cjs`, `node scripts/check-inline-navigation.cjs`, shared UI and SMS render checks. No production build was requested/run.

Actual phone/tablet GPS, camera/compression, permission/HTTPS behaviour, Google Maps rendering, background/visibility/buffer transitions, multi-user polling and responsive browser interactions still need a supervised one-vehicle pilot. These are not validated by server/render tests; do not call this production-certified fleet tracking yet.
